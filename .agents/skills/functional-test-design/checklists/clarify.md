# M1 需求澄清清单

在生成或修改 `requirements.yaml` 前逐项检查。先依据原始需求、已校验来源信封、项目 PRD 和靶应用事实判断是否适用；能由事实确定的不得重复询问，无法由事实确定且会改变验收的冲突才保留为澄清问题。

| ID | 主题与问题 | 可跳过条件 | 事实来源 |
| --- | --- | --- | --- |
| CL-UI-001 | 兼容与迁移：是否有旧流程、配置、数据或页面基线必须保持？ | 明确为全新流程且无存量约束 | accepted requirements、PRD、真实靶应用 |
| CL-UI-002 | 边界与分支：字段边界、枚举、空值、通过/拒绝分支是否决定不同的可观察结果？ | 来源明确没有边界或分支 | 需求来源、源码校验、靶应用行为 |
| CL-UI-003 | 权限与角色：哪些角色能操作，游客/登录态/不同权限看到什么？ | 所有角色明确同权且无登录边界 | 需求、路由/权限配置、靶应用 |
| CL-UI-004 | 失败与恢复：提交失败、超时、刷新、重复点击或部分成功后页面如何恢复？ | 同步只读展示且没有失败路径 | UI 源码、网络行为、需求验收条件 |
| CL-UI-005 | 并发与幂等：重复提交、重复加购或多标签页是否改变结果？ | 无写入动作且无重复触发路径 | 交互实现、接口行为、需求 |
| CL-UI-006 | 副作用与清理：用例 setup、提交、重试会创建/更新/删除哪些真实数据？ | 完整流程明确为只读 | 用例流程、API 行为、seed/reset 契约 |
| CL-UI-007 | 依赖与归属：本次结果依赖哪些上游状态，是否会影响其他 iteration 或共享资源？ | 无跨模块/跨 iteration 依赖 | traceability、fixture、项目结构 |
| CL-UI-008 | 来源基线：是否误把其他客户、版本、分支或 fixture 的文案/控件/状态带入本 iteration？ | 只使用当前 iteration 的已校验来源 | source manifest、目标应用 DOM、requirements |

## 判定与留痕

- `self-resolved`：事实足以决定答案；把结论写入 requirement 描述或 `requirements.yaml` 的 `source`，并保留可追溯来源。
- `skipped`：根据表中的条件明确不适用；在本轮交付说明记录条目和理由。
- `asked`：确实需要产品决定；写入 `requirements.yaml.ambiguities[]`，每轮最多 3 个最高优先级问题，并等待用户回答。回答后必须写 `resolved: true`、非空 `resolution`。
- requirements 被用户接受后，上游不可直接修改；新的事实或答案必须先用 `scripts/reopen_iteration.py` 重开。
