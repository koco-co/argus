# Risks & Known Issues

Limitations, instabilities, accepted debts, and rejected proposals. An entry here is a *record*, not an authorization to fix — fixes enter scope only when linked to a Roadmap task.

## Known Limitations, Instabilities & Tech Debt

| # | Issue | Type | Impact | Basis | Handling agreement | Status |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Secrets stored as plaintext in gitignored YAML (`env.*.yaml`, `notify.yaml`) | tech debt (accepted decision) | workstation/backup leak exposure; CI needs secret injection plumbing | PRD §6 explicitly chose lightweight posture | v1 accepted; v2 must migrate to env-var/secret-manager sources; `check_secrets.py` blocks accidental commits only | Accepted debt |
| 2 | Static SQL write-detection is inherently incomplete (dynamic SQL, driver-native calls) | limitation | regex/denylist layers can be evaded by determined or buggy code | review consensus; DB-role is authoritative | treat code layers as defense-in-depth only; real control = SELECT-only DB role (Architecture §6 layer 1) | Accepted |
| 3 | Layering/path scans are AST-level; they cannot prove absence of every devious runtime read of `iterations/**` from automation code | limitation | rare crafted bypasses could couple tests to iteration data | Architecture §3 honest-limits note | residual risk accepted for v1; patterns extended as observed | Accepted |
| 4 | Single long-lived `release` branch does not support concurrent in-progress iterations | design constraint | multi-team parallel work must wait or use a future asset-ownership design | ADR-001, v1 single-in-progress rule | v1 validation rejects a second non-terminal iteration; revisit branch/asset model post-v1 | Deferred |
| 5 | `.claude/skills/` symlinks need elevated mode on Windows | limitation | Windows contributors need developer-mode/symlink privileges | review note (Qwen/Kimi) | POSIX-first docs; converters allowed to use directory-copy fallback | Accepted |
| 6 | Self-debug repair quality depends on underlying model capability (evidenced: seven models reviewing this same design produced wildly divergent verdicts) | instability | weaker sessions burn budget without valid repairs; risk of noisy escalations | variance across the archived seven-model review record (consumed 2026-08-27, removed thereafter by owner decision) itself | budgets cap cost; escalation classes stop wrong-direction work; acceptance diff-review is the human backstop | Mitigated-by-design |
| 7 | XMind/xlsx byte-reproducibility pins exporter library versions | maintenance coupling | exporter upgrades may break byte-equality with historical exports | DATA_MODEL conventions | exports are point-in-time artifacts; reproducibility asserted per current lockfile, not retroactively | Accepted |
| 8 | Allure HTML report generation requires the separate allure CLI — no task installs it | known gap | `reports/allure-report/` stays empty; results JSON remains the artifact of record | GLM P2 note | v1 treats allure-results + run-summary as deliverables; HTML gen optional local tooling | Accepted gap |
| 9 | `knowledge/` flat files will degrade at scale | future debt | grep-unwieldy retrieval as entries accumulate | PRD §8 defers categorization deliberately | revisit trigger pre-agreed: categorize once grepping hurts | Deferred |
| 10 | Multi-statement SQL strings are rejected outright by ReadOnlyDBClient (no batch reads) | limitation | an assertion needing several statements makes several calls instead | Architecture §6 | acceptable; keep one statement per query call | Accepted |
| 11 | Worker-isolated browser/session fixtures require careful pytest-xdist integration | implementation risk | an incorrect fixture scope can reintroduce cross-worker contamination or false flake diagnoses | ADR-008, Roadmap 5.1 | prove with a repeated multi-worker module run before relying on parallel regression execution | Open until Phase 5.1 |
| 12 | Approval authenticity rests on process (record_approval.py sole-writer + review), not cryptographic receipts | limitation | an agent that also edits `iterations/**` could fabricate approval history; digests are now redacted-copy based (PRD §6), which removes brute-force leakage but not forgery | GPT-review adoption decision (single-operator v1) | host discipline + acceptance review are the v1 backstop; introduce signed receipts when a second operator/platform appears | Accepted, revisit trigger recorded |
| 13 | No cross-iteration stable IDs or canonical requirement/spec model — lineage is per-iteration only | future debt | "which old requirements did this change affect / which automation still covers them" requires manual trace reading across iterations (mitigated slightly by case title/module columns kept in traceability rows for grep-ability) | GPT-review + post-v1.4 review (OpenSpec-style delta models considered) | observable reopen trigger: a second target-app requirement appears, or `iterations/` count grows while `automation/` sees cross-iteration rewrite conflicts; candidate designs: stable UIDs + change packages (Deferred list) | Deferred |
| 14 | Framework core (schemas/checkers/scripts) and project assets share one repo/package without version boundary | design constraint | onboarding a second target project would fork the core via copy instead of versioned reuse; per-project schemas then drift independently | ADR-007 posture; core/adapter proposal rejected for single-project v1 | concrete reopen signals: a second target-app requirement, or the first copy-fork attempt; then split core package (schemas+checkers+scripts+skills) vs project adapter (config/seed/notes/denylist) with a conformance suite | Deferred |
| 15 | Semantic fake-green defenses are heuristic: structural freezing + mechanical preclassification + canary seeds + literal-return heuristic, not adversarially complete | limitation | sophisticated in-allow-list gaming (request interception, cross-file constant plumbing) could still pass static gates while asserting nothing real | GPT-review citing NIST agent-eval findings; post-v1.4 review added the cheap stub-return detection layer | trace-mandatory evidence + human acceptance diff review are the designed backstop; independent oracle services stay post-v1 | Mitigated-by-design |
| 16 | Generated code executes inside the operator's own environment (no container sandbox in v1) | accepted debt (reaffirmed) | buggy generated code runs with operator privileges; secrets posture per #1 applies | prior rejection of bandit/container gate reaffirmed against OWASP-based minimum-sandbox argument (GPT-review) | minimum hygiene instead of sandboxing: credentials only enter through config loading path; egress needs arise explicitly and are reviewable at acceptance; revisit on team growth | Accepted debt |

## Rejected Review Proposals (recorded so they aren't re-raised without new evidence)

A rejection is not a permanent ban: re-raise becomes appropriate when its recorded assumptions change (new scale, new operators, incident evidence). Each row lists the standing assumption so superseding is easy.

| Proposal (source noted) | Why not adopted | Standing assumption / reopen trigger |
| --- | --- | --- |
| Hard bandit/container-scan gate on generated code before execution (Kimi; reaffirmed-as-rejected by GPT's OWASP minimum-sandbox argument) | Heavyweight for single-operator v1; execution stays inside the operator's project environment. Deferred list captures post-v1 hardening. | Single trusted operator; team growth or untrusted-code workloads reopen it (risk #16) |
| Replace read-only verb allow-list with sqlparse/pglast parsing (Kimi/Grok) | Dependency weight vs benefit; leading-keyword allow-list plus authoritative DB role covers the practical threat model (Architecture §6 rationale). GPT's WITH-CTE sharp edge adopted as fail-closed token scan instead. | Static layer stays defense-in-depth; role remains authoritative regardless of parser choice |
| Global cross-repo RTM aggregation service (Gemini) | Post-v1; single repo, file-based traceability suffices now. | Single repo/project scale; see risk #14 for the packaging trigger |
| Numeric SLOs for framework operations ("generation < 30s" etc.) (Kimi NFR) | Arbitrary without measurement history; would be decorative contract numbers. Revisit with real telemetry after Phase 9. | Any measured telemetry baseline |
| Mandatory user confirmation gate after M3 case export (Grok; Spec Kit/OpenSpec analogy re-raised by GPT #16) | Deliberate pipeline trade-off retained; implicit review opportunity documented (PRD §4.3) since M6 invocation is itself a natural pause the user controls, and M2/M9 carry hard gates. | Evidence that schema-valid cases routinely misread business rules despite M2 review |
| Coverage quota percentages for framework's own test suite (various) | Replaced by fixture-pair completion rules (TESTING_STRATEGY coverage section). | Fixture-pair rule proving insufficient regression net |
| Cryptographic approval receipts w/ challenge-response (GPT #8) | No better anchor than host process discipline in single-operator v1; sole-writer tooling + redacted digests chosen. Second operator/platform = reopen trigger (risk #12). | Multi-operator context or compliance demand |
| Full multi-input provenance graph with producer metadata baked into every artifact (GPT #10) | Direct-parent hash chain + optional `inputs[]` + events/skill-version attribution fits audit needs at v1 scale without inflating every artifact. | Staleness false-negatives observed in practice |
